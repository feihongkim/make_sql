## 1. 새로 생긴 것 — `./abledb ask`

컨테이너에서 **실행 중인** Claude Code 세션에 요청을 넣고 응답을 받는다.

```bash
./abledb ask apply_claude "이어서 이것도 해줘"                    # 문맥 유지
./abledb ask apply_claude --new "이 로그 요약해줘"                # 문맥 격리
./abledb ask apply_claude --file report.md --new "경고만 뽑아줘"  # 큰 자료 전달
./abledb ask tem_lms @task.txt --host alvinii --timeout 1800     # 원격 호스트
```

| 옵션 | 뜻 |
|---|---|
| (기본) | **채널 모드.** 살아 있는 세션에 주입 → 문맥이 이어진다. 큐 직렬 처리 |
| `--new` | **일회성.** `claude -p` 를 새로 실행. 문맥 없음, 세션 오염 없음, 큐 무관 |
| `--file 경로` | 자료를 컨테이너 `/tmp` 로 올리고 **경로만** 프롬프트에 넣는다. 반복 지정 가능 |
| `--host 이름` | 원격 호스트 SSH |
| `--timeout 초` | 기본 900 |

**모드 고르는 기준**

- 앞 작업을 이어가야 함 → 채널 모드
- 요약·분석·정기 배치처럼 세션을 더럽히면 안 됨 → `--new`
- 큰 문서를 넘김 → `--file` + `--new`
  (인라인 `@파일` 은 내용이 세션 컨텍스트에 **영구히** 남는다. 1.5MB 를 넣으면 그 세션은 사실상 못 쓴다)

구현: `srv/agent_ask.go`

### 어떻게 동작하나

Claude Code 의 **channel** 을 쓴다. channel 은 `experimental['claude/channel']` 을 선언한
MCP 서버로, 텔레그램 플러그인이 쓰는 바로 그 메커니즘이다.

```
POST /run → notifications/claude/channel → (이미 떠 있는 세션) → reply 툴 → HTTP 응답
```

`agentapi` 플러그인이 컨테이너 안 `127.0.0.1:8799` 에 뜬다. 포트를 publish 하지 않고
`docker exec ... curl` 로 접근하므로 인증·포트 할당표가 필요 없다.

## 2. 제거된 것 — `docker-claude`, `send`

둘 다 `docker exec <c> claude -p` 였다. 세 가지가 문제였다.

1. 같은 봇 토큰으로 **두 번째 텔레그램 MCP 서버**가 떠서 409 Conflict → 원래 봇이 죽는다
2. 새 프로세스라 **세션 문맥이 끊긴다**
3. `-u node` 가 박혀 있어 런북 컨테이너(`usermod -l feihong`)에서는 **실행조차 안 됐다**

대상 컨테이너도 사라졌다. 예전 CLAUDE.md 가 나열하던 `*_claude` 15개는 **중지된 상태로도
존재하지 않고**(`docker ps -a` 에서도 0개), 함대는 `_pi` 로 이전됐다. `_pi` 컨테이너에는
`claude` 바이너리 자체가 없다.

일회성 실행이 필요하면 `ask --new` 를 쓴다.

## 3. 스케줄러

### 3-1. 패닉 복구

`dispatch` 가 띄우는 goroutine 에 `recover()` 가 없어, 작업 하나가 패닉하면 **스케줄러
프로세스 전체가 죽었다.** 스케줄러는 다른 프로세스를 감시하는 쪽인데 정작 자신이 가장
약했다.

이제 패닉을 기록하고 Telegram 으로 통보한 뒤 다음 tick 을 계속 돈다.
검증을 위해 작업 실행부를 `runTask` 로 분리하고 `execTask`/`notify` seam 을 두었다
(동작은 그대로). 테스트에서 패닉을 주입해 복구를 확인할 수 있다.

### 3-2. systemd user 유닛

`nohup` 으로만 떠 있어 죽으면 아무도 다시 띄우지 않았다.

**system 이 아니라 user 단위다.** 이 호스트의 sudo 는 비밀번호를 요구하므로,
`/etc/systemd/system` 에 두면 제어할 때마다 sudo 가 필요하고 **비대화형 에이전트가
스케줄러를 재시작할 수 없게 된다.**

```bash
systemctl --user status abledb-scheduler
systemctl --user restart abledb-scheduler      # 재빌드 후 반드시 필요
systemctl --user stop abledb-scheduler
journalctl --user -u abledb-scheduler -f       # systemd 이벤트
tail -f test_logs/scheduler_systemd.log        # 작업 로그 (여기가 본체)
```

**주의 3가지**

- `./abledb_Hope scheduler stop` 은 이제 **무력하다.** SIGTERM 을 보내도 `Restart=always`
  로 10초 뒤 되살아난다. 멈추려면 `systemctl --user stop`
- 코드를 고치면 **재빌드 + `systemctl --user restart`** 를 해야 새 바이너리가 적용된다
- `./run.sh scheduler` 를 실행하지 말 것. 두 번째 인스턴스를 띄우려다 PID 검사에 걸린다.
  빌드만 하려면 `go build -o abledb_Hope .`

`Linger=yes` 로 설정돼 있어 로그아웃·재부팅에도 유지된다.

### 3-3. 작업 등록 테이블 + 기동 시 검증

작업 이름과 실행 함수가 문자열 `switch` 로만 연결돼 있었다. `BuildSchedule` 에만
작업을 추가하고 실행 함수를 빠뜨려도 **컴파일·기동이 모두 정상**이고, 발동 시각에
"알 수 없는 명령" 로그 한 줄만 남는다. 그런데 `dispatch` 는 **실행 전에 완료로 기록**하므로
그날 다시 시도하지 않는다 — 조용히 매일 건너뛰고 알림도 없다.

```go
var taskRunners = map[string]func(*Scheduler, []string){ ... }   // 12개

func validateSchedule(tasks []Task) error { ... }                // run() 시작 시 호출
```

map 으로 바꾼 것은 문법 취향이 아니라 **검증 때문**이다. `switch` 는 case 목록을
프로그램이 읽을 수 없어 짝을 맞춰볼 수가 없다. 이제 짝이 안 맞으면 기동 즉시 종료한다.

```
[scheduler] 스케줄 구성 오류: 태스크 "new_thing" 의 명령 "new-thing" 에
            대응하는 실행 함수가 taskRunners 에 없습니다
```

### 3-4. 테스트 7개 (저장소 최초)

```

TestRecoverTaskSurvivesNotifyFailure     알림 전송 실패해도 복구는 성공

TestValidateScheduleCatchesMissingRunner 오타·빈 명령을 잡는지

```

첫 번째는 복구가 없으면 **테스트 프로세스 자체가 죽어** 실패한다. 회귀를 실제로 잡는다.

```bash
go test ./...      # ok MakeSQL/scheduler
go vet ./...       # 경고 0
```

## 4. 반드시 알아야 할 함정

이 절이 이 문서에서 가장 중요하다. 전부 **조용히 실패**한다.

### 4-1. 채널 서버에서 `process.stdin` 을 건드리면 안 된다

`process.stdin` 에 `'end'`/`'close'` 리스너를 붙이면 stdin 이 flowing 모드가 되어
`StdioServerTransport` 가 읽어야 할 MCP 메시지를 가로챈다. 서버가 기동 직후 죽는다.
종료는 `SIGINT`/`SIGTERM` 으로만 처리한다.

### 4-2. 서버가 죽으면 그 흔적이 전 컨테이너로 전파된다

채널 MCP 서버가 비정상 종료하면 Claude Code 는 "인증 필요"로 판단해 기록한다.

```bash
cat ~/.claude/mcp-needs-auth-cache.json
#  { "plugin:agentapi:agentapi": { "timestamp": ..., "id": "..." } }
```

- **호스트 공유 경로다.** 한 컨테이너에서 생긴 기록이 전 컨테이너에 전파된다
- `docker compose up -d --force-recreate` 로도 복구되지 않는다
- debug 로그에 에러가 아니라 **`Starting connection` 줄이 통째로 사라지는** 형태로만
  나타난다. 플러그인 로드는 정상으로 찍혀서 더 헷갈린다

복구: `rm ~/.claude/mcp-needs-auth-cache.json` 후 컨테이너 재시작.
원인이 된 서버 버그를 먼저 고치지 않으면 다음 기동에서 다시 기록된다.

### 4-3. 일회성 `claude -p` 도 플러그인 MCP 서버를 띄운다

`-p` 모드라고 예외가 아니다. 컨테이너 안에서 일회성 실행을 하면 이미 떠 있는 채널 서버와
**포트가 충돌**하고, 그 실패가 4-2 의 캐시를 만들어 다음 재시작부터 채널을 죽인다.
실행 직후에는 멀쩡해 보이므로 더 위험하다.

→ `ask --new` 는 두 플러그인을 모두 `false` 로 명시한 **전용 `settings-oneshot.json`** 을 쓴다.
`settings-notelegram.json` 재사용은 금지 (agentapi 가 `true` 라 충돌).

### 4-4. marketplace 원본은 `~/.claude` 안에 있어야 한다

`known_marketplaces.json` 이 절대경로를 저장하는데, 컨테이너에 마운트되는 건 `~/.claude`
뿐이다. 밖에 두면 `Marketplace ... failed to load: cache-miss` 로 조용히 로드되지 않는다.
**심볼릭 링크도 안 된다** (컨테이너 안에서 링크 대상이 없다).

### 4-5. 텔레그램 봇 확인용 `getUpdates` 는 1회만

플러그인은 409 를 8회까지만 재시도하고 **폴링을 영구히 포기**한다
(`if (is409 && attempt >= 8) ... Exiting`). 확인 명령을 연달아 돌리면 봇이 죽는다.
`ok:true` 가 나오면 `docker compose restart` 후 다시 1회만 확인한다.

컨테이너를 연속 재시작해도 같은 일이 생긴다 (이전 봇이 토큰을 놓기 전에 새 봇이 시도).

**MakeSQL 자체의 컨테이너화.** 코드가 호스트를 직접 조작한다 —
`ask` 는 docker.sock, `process-check` 는 호스트 `ps`, `code-backup` 은 `/home/feihong/code/`
전체, 나머지는 5개 호스트 SSH 키가 필요하다. 컨테이너에 넣으려면 `docker.sock` +
`--pid=host` + 홈 마운트 + SSH 키를 다 줘야 하고, 그 시점에 **호스트 권한과 동등**해져
격리 이득이 없다. 특히 `process-check` 는 `--pid=host` 없이는 자기 자신만 보여 무력해진다.

에이전트(`makesql_pi`)는 이미 컨테이너, CLI·스케줄러는 호스트 네이티브 — 이 분리가 맞다.
자동 재기동이 목적이었다면 systemd user 유닛이 이미 같은 것을 제공한다.
